# Концепція Phantom OS та Архітектура Чатового Вікна

Цей документ містить повний опис концепції автономної ШІ-системи **Phantom OS**, її взаємодії з користувачем, а також детальний технічний опис роботи чатового вікна та комунікаційного стеку.

---

## 1. Концепція Phantom OS (Sentient Familiar AI-OS)

**Phantom OS** — це локальна автономна операційна система (або десктопна оболонка), спроєктована для Radxa + ESP32 (Embedded Kiosk) з можливістю запуску у вигляді нативного десктопного додатку через Tauri 2.x + Python.

Головна відмінність Phantom OS від класичних чат-ботів — концепція **Sentient Familiar (Фамільяра)**. ШІ не просто відповідає на запити, а є «живою» сутністю, яка спостерігає за станом пристрою, довкіллям (через ESP32-сенсори) та користувачем, адаптується до поведінки та проактивно діє.

### 1.1 Роль та поведінка Фамільяра (Familiar behavior)
Фамільяр представлений на екрані як напівпрозорий скляний людиноподібний персонаж (glassmorphic humanoid entity ~110x138px) з теплими бурштиновими суглобами. Він використовує процедурну анімацію та кінематику (Inverse Kinematics) для взаємодії з DOM-елементами інтерфейсу.

Фамільяр є фізичним відображенням станів вбудованої машини станів (Core State Machine) через візуальну систему **Sunrise**:

| Стан (State) | Візуальна поведінка Фамільяра | Опис стану в системі |
| :--- | :--- | :--- |
| **`SHADOW`** | Peeking (виглядає з краю екрана) | *«В тіні. Спостерігаю.»* Збір сенсорних даних без активної взаємодії. |
| **`FOCUS`** | Idle (спокійне літання на місці) | *«Фокус. Тримаю шум низько.»* Режим підвищеної продуктивності, мінімізація сповіщень. |
| **`DIALOGUE`** | Waving/Happy (привітання, радість) | *«Я тут.»* Активний голосовий або текстовий діалог з користувачем. |
| **`SENTINEL`** | Pointing (вказує на елементи інтерфейсу) | *«Аномалія. Дивись сюди.»* Попередження про критичні зміни сенсорів чи безпеки. |
| **`GHOST`** | Vanishing (розчиняється в тумані) | *«Зникаю з поверхні.»* Режим підвищеної конфіденційності, шифрування PII. |
| **`DREAM`** | Sleeping (спить, з'являються літери zZz) | *«Консолідую пам'ять.»* Фоновий аналіз, архівація логів, ChromaDB-індексація. |
| **`OPERATOR`** | Floating (вільно дрейфує по екрану) | *«Операторський режим.»* Пряме виконання термінальних інструкцій розробника. |

## 2. Архітектура та Робота Чатового Вікна (Chat Communication Stack)

Чатове вікно в Phantom OS — це не просто поле введення тексту, а складний вузол інтеграції асинхронного FastAPI-бекенду, WebSocket-стрімінгу, локальної векторної пам'яті та **Generative UI**.

### 2.1 Потік Даних при Відправці Повідомлення (Data Flow)
Коли користувач надсилає повідомлення у чат:
```
[User Input: Text/Voice]
       │
       ▼
1. REST API: POST /chat/message (routes_chat.py) ──► commit optimistic user message to DB
       │
       ▼
2. Prompt Builder (prompt_builder.py):
   - Отримує ContextSnapshot (дані сенсорів CPU, RAM, GPS, біометрії користувача).
   - Запитує ChromaDB (векторна пам'ять) -> дістає Top-5 релевантних спогадів.
   - Запитує SQLite -> дістає поведінкову модель користувача (behavioral model) для адаптації тону.
   - Генерує фінальний системний промпт.
       │
       ▼
3. AI Router (provider.py):
   - Надсилає запит до Gemini API (первинний) || Ollama Llama-3 (локальний fallback при таймауті).
       │
       ▼
4. Response Formatter (response_formatter.py):
   - Аналізує відповідь моделі. Якщо ШІ викликав respond_artifact() або інший інструмент,
     формує відповідний віджет (Generative UI) та приєднує його як Scene у JSON-відповіді.
       │
       ▼
5. WebSocket Hub (websocket_hub.py) & HTTP Response ──► Фронтенд рендерить віджет у реальному часі.
```

### 2.2 Generative UI (React Artifacts)
Коли користувач просить намалювати графік, створити калькулятор чи трекер звичок, ШІ викликає спеціальну форму відповіді:
- **`respond_artifact`** (параметри: `title`, `code`): передає повноцінний React-код (JSX/TSX) із використанням Tailwind CSS та іконок `lucide-react`.
- Фронтенд отримує цю форму відповіді, динамічно монтує компонент через пісочницю `SceneArtifactPanel` та відображає інтерактивний віджет безпосередньо всередині чату.

### 2.3 WebSocket-стрімінг та Захист від Витоків (Session Isolation)
- Для створення ефекту миттєвого відгуку (TTFT < 500ms) бекенд використовує генератор стріму. Кожна літра (дельта) відповіді надсилається через WebSocket-канал `chat` із типом події `"stream"`.
- Для запобігання багу, коли стрім-потік або фінальне повідомлення відображалися не в тому чаті, куди їх надіслали (якщо користувач перемикав сесії під час генерації), до кожної події `"stream"` та `"message"` на бекенді прикріплюється `session_id`.
- Фронтенд (`useChatStream.ts`) строго фільтрує вхідні WebSocket дельти за ідентифікатором сесії:
  ```typescript
  if (!session_id || session_id === state.currentSessionId) {
      state.setStreamChunk(message_id, delta, done, message);
  }
  ```

### 2.4 Session-Specific Введення та Запобігання Lockout
Щоб користувач не був заблокований в інтерфейсі, поки триває довга генерація відповіді:
- У [chatStore.ts](file:///home/radxa/programming/my_own/phantom_ai/PHANTOM_OS_BLUEPRINT/phantom-os/src/frontend/src/stores/chatStore.ts) реалізовано локальний реєстр активних відправок `sendingSessionIds: Record<string, boolean>`.
- Коли повідомлення надсилається в Сесію А, статус `sending: true` встановлюється тільки для Сесії А.
- При перемиканні на Сесію Б поле введення одразу розблоковується, і користувач може писати нове повідомлення, в той час як Сесіння А продовжує тихо отримувати чанки генерації в бекграунді.

### 2.5 Автоматичне Очищення Порожніх та Зламаних Сесій
Якщо під час ініціалізації чату чи генерації відповіді виникла помилка (наприклад, модель повернула порожній бабл і бекенд згенерував системну заглушку-помилку *"Не встиг сформулювати — перепитай?"*):
- При кожному запиті списку чатів (`GET /sessions`) бекенд автоматично видаляє «засмічувальні» сесії:
  ```python
  # Видаляються сесії з message_count == 0
  # Видаляються сесії з message_count <= 2, де відповіддю є заглушка "Не встиг сформулювати..."
  ```
- Це підтримує бічну панель історії в чистоті, прибираючи невдалі спроби з'єднання.

### 2.6 Автоматична Генерація Назв Чату (Summary)
Назва чату створюється повністю асинхронно та автономно:
1. Коли кількість повідомлень у чаті стає рівною **2** (перший запит користувача + перша відповідь ШІ) і сесія ще не має назви.
2. Бекенд запускає фонову задачу, яка відправляє короткий запит (`chat_subtask`) до Gemini:
   - Промпт: *"Summarize this chat in 2-4 words maximum, capitalize it like a title. Return ONLY the title and nothing else."*
3. Отриманий результат (наприклад: *«Аналіз Метрик»* або *«Трекер Звичок»*) зберігається як заголовок сесії в базі даних SQLite та відображається в інтерфейсі.
