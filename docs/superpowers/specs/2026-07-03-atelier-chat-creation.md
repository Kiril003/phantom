## 2. Цільовий рівень — чотири стрибки

### A. Workbench: справжні проєкти замість srcdoc-рядка
Робочий простір на диску (`~/.phantom/works/<id>/`): багатофайловий проєкт
(React/Vite, Three.js, D3, static site — будь-що), git-версіонований.
Backend піднімає **sandboxed preview server** (localhost, ефемерний порт,
без зовнішньої мережі) — чат вбудовує iframe на нього. Це вже не «віджет»,
а працюючий сайт/застосунок, який можна відкрити на весь екран, тицяти,
перезавантажувати. Ліміт: N активних workbench-ів (борд!), LRU-зупинка.

### B. SEE → CRITIQUE: творіння, що бачить себе (Law 6)
Після кожного паса: headless screenshot рендера (playwright уже в стеку
агента / або screen_capture) → мультимодальний виклик «оціни проти брифу»
→ вердикт + патч **конкретних файлів** (не регенерація блоба). Цикл
skeleton → layout → interactions → polish, кожна фаза — facet-картка в
чаті (розширення наявного on_phase). Це головна різниця з «згенерував і
молюсь»: складне стає рутиною, бо модель дивиться і править.

### C. Живі дані: візуалізація як орган, не як знімок
Типізований data-feed контракт для артефактів/workbench-ів: підписка на
WS-канали (sensors, map, will journal, system) через існуючий postMessage
broker — дашборд диха́є реальними даними PHANTOM у реальному часі.
Curated allowlist каналів = той самий security-модель, що в widgets-спеці.

### D. Довговічність і промоушн
- Великий творчий джоб = **Foundry-задача** (F2): контракт → чекпойнти →
  переживає рестарт; чат показує прогрес, оператор може втрутитись.
- «Deploy as app»: вдалий workbench промотиться в постійний застосунок
  (app switcher / tools) — розширення наявного «save as tool».

## 3. Порядок впровадження (кожен крок самодостатній)

1. **W1 Workbench core** — workspace на диску + preview server + iframe
   сцена `workbench` + list/stop API. (Фундамент; без нього решта не має
   де жити.)
2. **W2 SEE→CRITIQUE** — screenshot→critique→patch цикл поверх W1, фази в
   чат через on_phase. Гейт: демо «зроби лендінг з анімацією» проходить
   ≥2 самокритичні ітерації без людини.
3. **W3 Live data feeds** — broker-розширення: subscribe(channel) з
   allowlist; перший демо-дашборд на живих сенсорах.
4. **W4 Foundry-інтеграція + deploy-as-app** — після F2; до того W1-W3
   живуть як звичайні задачі.

Залежності: W1-W3 не чекають FORGE-фаз (працюють на нинішньому кістяку);
W4 чекає F2. G1 (один ToolRegistry) зробить брокер дій чистішим, але не
блокує. На борді SEE-цикл лімітувати: 1 паралельний critique, бюджет
токенів на джоб (Law 7).

## 4. Чому це «зовсім інший рівень», а не фіча

Сьогоднішній артефакт — листівка. Workbench+SEE — **майстерня, де істота
працює на очах**: вона будує, дивиться на результат, критикує себе,
править — а ти бачиш кожну фазу і можеш сказати «стоп, синій не той».
Жоден чат-продукт не дає одночасно: справжній багатофайловий проєкт +
самокритичний зоровий цикл + живі дані власного тіла + промоушн у
постійний орган системи. Це і є різниця між «генерує HTML» і «творить».
